# Phase one application contract

Current workspace schema is10. The Schema10 section below governs extraction persistence, review and recovery; it supersedes historical whole-document commit and retry behavior in the phase-two/three sections. Completed extraction/organization, retrieval/context/refusal and QA-efficient rounds are historical runs. The current QA-calibration round retains numbered spans and a revalidated partial fallback, adds obligation/per-unknown consistency and bounded scope navigation, and improves source-position/independent-stage selection while preserving literal extraction v6, current-version eligibility and exact claim-anchor checks.

## Schema 8: memory workbench

- `get_assistant_preferences {}` → `{role,answerStyle,reportFormat,reminderStyle,version,updatedAt}`. Defaults: empty role, `standard`, `structured`, `standard`.
- `save_assistant_preferences {baseVersion,role,answerStyle,reportFormat,reminderStyle}` → updated preferences. Role ≤1000 characters; answerStyle=`standard|concise|detailed`, reportFormat=`structured|brief`, reminderStyle=`standard|gentle|direct`. Stale version returns `REVISION_CONFLICT`.
- `clear_assistant_preferences {baseVersion}` → defaults with a new version. Removes current preference text; previous exported backups are unaffected.
- `get_project_brief {projectId,date}` → `{projectId,brief:null|{date,createdAt,fingerprint,stale,sections,pendingReviews,limitations}}`. Date is ISO `YYYY-MM-DD`. Read computes current staleness without changing the saved snapshot.
- `generate_project_brief {projectId,date}` → same shape; replaces the project's latest derived snapshot using local records. Each section item is an assistant reference with its frozen record and supported navigation/evidence fields. Never creates memory or model requests.
- `get_memory_quality {projectId?}` → `{corrections,assessments,counts,limited,checkedAt:null}`. Up to 200 latest corrections and 100 latest assessments; counts aggregate all manually labelled snapshots in scope.
- `check_memory_quality {projectId?}` → same shape with retrieval-only correction checks (`passed|not_recalled|superseded`) and checkedAt. Uses current project memory retrieval without a model; check results are transient. Does not measure answer or extraction correctness.
- `assess_extraction {candidateKind,candidateId?,sourceId?,verdict,errorKind,reason?}` → quality for the candidate's project. Kinds: `memory|task|source`. Memory/task must be unedited AI candidates; source uses sourceId and records an omission. Verdict=`correct|incorrect`; errorKind=`none|content|assignee|date|status|evidence|omission`. Correct requires none; incorrect requires a nonempty reason ≤2000 characters. Source requires incorrect/omission. Snapshot labels are upserted by a deterministic hash so repeated saves do not inflate counts.

`get_state` includes `assistantPreferenceVersion`. Personal assistant retrieval v4 includes explicit preferences and question intents in its fingerprint; in-flight model answers are invalidated by preference changes. Connector QA does not receive personal preferences. Daily report basis freezes reportFormat; missing format in historical records retains the original renderer. All new tables are stored in project SQLite, migrated transactionally and included in backup validation/restoration. These preferences are user text, not credentials or authority to execute actions.

## Personal Feishu assistant extension

`ask_project {projectId,question}` performs read-only retrieval over the project's active current confirmed memory, then a model answer. Returns `{answer,citations,grounded,context,queryTrace,qualityReview?}` plus normalized claims/status/uncertainty. Generation outputs integer `referenceIndex/spanIndex` selections; Rust resolves them to exact current anchors and public citation IDs. With configured material access, an unknown, partial, background-only or semantically rejected first answer may trigger one targeted query rewrite (up to3 strings, each2–160 characters) and scoped re-retrieval. Query strings are not evidence and cannot select scope or execute tools. Every model-generated grounded answer receives separate support, direct-answer and completeness review, including exact single-claim quotations. Review transport/format failure stops without initiating a supplement. A failed supplement may only return the first already-reviewed grounded partial after revalidating both snapshots; otherwise it refuses. Maximum5 model calls,180000 cumulative input/schema characters and16000 parsed output characters per call, with the saved timeout shared across the entire model phase. Provider-reported cumulative usage reaching60000 tokens prevents further calls; this is a post-response stop threshold, not an exact preflight token cap. No automatic network retry. Citations carry the current revision and its evidence. Actor-owned snapshots carry workspace epoch and model settings revision; changes during generation, review, rewrite or fallback reject stale answers. Extraction material consent also gates remote QA; unavailable consent/model access returns an ungrounded connector result without a request.

`get_feishu_status {}` returns redacted settings, personal authorization status, runtime status, and recent delivery records. `save_feishu_settings {appId,appSecret?,enabled,pollIntervalSeconds,replyPrefix,bindings:[{chatId,projectId,enabled}]}` validates local project IDs and updates device settings. `begin_feishu_authorization {}` returns `{authorizationUrl,redirectUri,expiresAt}` and starts a state-checked loopback OAuth callback. `disconnect_feishu {}` clears local personal authorization and disables delivery. `poll_feishu_now {}` requests an asynchronous poll. `list_feishu_chats {}` returns `{chats:[{chatId,name}]}` from personal authorization.

The connector uses personal OAuth credentials only and searches new mentions of the authorized user inside explicitly bound enabled group chats. Delivery receipts have persistent message-ID deduplication outside project backups. Restore pauses the connector before changing project state. Network operations run outside the database actor and reuse its existing Engine rather than opening another workspace instance. Configuration and tokens are device-local, private, redacted, and excluded from project backups. See [setup and operational behavior](feishu-personal-assistant.md).

The Rust core owns all persistent state. React uses a single `execute` Tauri command with `{ request: { command, payload } }`. Payloads and response objects use camelCase. Commands return JSON data or an error `{ code, message }`. There is no model connection in phase one. A user creates a proposal from source segments, then explicitly confirms it.

Core public API: `Engine::open(root: impl AsRef<Path>) -> Result<Engine, AppError>`; cloneable Engine; `Engine::execute(request: Request) -> Result<serde_json::Value, AppError>`; `Request { command: String, payload: serde_json::Value }` (serde). A dedicated database thread owns the connection; parsing is outside the database actor. On startup pending/interrupted imports resume from persisted originals. All tests use isolated workspace directories.

## Commands

* `get_state {}` → `{ workspace, projects, sources, proposals, memories, jobs, backups }`.
* `create_project { name, description? }` → Project.
* `import_text { projectId, title, text, sourceAt? }` → `{ jobId, duplicate, sourceId }`.
* `import_file { projectId, filename, contentBase64, sourceAt? }` → same result. Inputs are user-selected file bytes; never arbitrary renderer-supplied filesystem paths. Support TXT/MD/DOCX/text PDF, with an explicit failure for empty/scanned PDF. File limit 10 MiB.
* `get_source { sourceId }` → `{ source, segments }`.
* `create_proposal { projectId, sourceId, segmentIds, kind, content }` → Proposal. Evidence must belong to that project/source; content and at least one segment are required.
* `confirm_proposal { proposalId }` → Memory summary. Repeating confirmation is idempotent.
* `reject_proposal { proposalId }` → Proposal.
* `get_memory { memoryId }` → `{ memory, revisions }`, each revision includes its evidence array.
* `revise_memory { memoryId, baseRevision, content, reason, segmentIds?, question? }` → Memory summary. Reject stale baseRevision. Empty segmentIds means a personal correction, not a claim supported by old evidence. Schema 8 also atomically stores a correction sample with the previous and corrected revisions; optional question is limited to 2000 characters.
* `create_backup {}` → Backup record. A ZIP with manifest, consistent SQLite snapshot, and original files; excludes backups. Verify checksums and schema/integrity before restore.
* `inspect_backup { filename, contentBase64 }` → `{ formatVersion, createdAt, counts, compatible }`.
* `restore_backup { filename, contentBase64, confirmation: "RESTORE" }` → `{ safetyBackupId, counts }`. Validate fully first; automatically retain a safety backup of current state. Running imports cannot write old results after restoration.

## Phase two: AI extraction (authoritative additions)

Settings are device-local, excluded from backups. Raw API keys are never returned, stored in SQLite, included in jobs, sent to the renderer on reads, or logged. Defaults: provider=openai_compatible, baseUrl=https://api.deepseek.com, model=deepseek-flash, outputFormat=json_object, timeoutSeconds=60, autoExtract=false, remoteConsent=false. DeepSeek JSON mode uses response_format=json_object with JSON instructions. Ollama remains an optional loopback-only provider.

### Commands

- `get_ai_settings {}` -> AiSettingsPublic.
- `save_ai_settings {provider,baseUrl,model,outputFormat,timeoutSeconds,autoExtract,remoteConsent,apiKey?}` -> AiSettingsPublic. Omitted apiKey retains the existing key ONLY when provider and normalized baseUrl are unchanged; empty string clears it. Endpoint changes clear the key unless explicitly replaced. Settings/key are a private local file (directory0700/file0600), never part of a ZIP. Enabling autoExtract affects future imports only; never silently scans existing ready sources.
- `test_ai_connection {}` -> `{ok:true,message,models:string[]}`. Tests SAVED config with a small synthetic structured extraction request, sending no project material; runs outside DB actor. Validates the selected model/auth/output shape, not just GET models.
- `start_extraction {sourceId}` -> Job. Explicitly starts extraction for ready source with saved valid config/remoteConsent, even when autoExtract=false. Returns existing queued/running job for source; a completed prior run can produce a new run but exact candidate fingerprints never reappear (including ignored/confirmed).
- `retry_extraction {jobId}` -> Job. Failed/cancelled job only. With the same source/configuration/prompt snapshot it increments attempt/generation and reuses the job and successful checkpoints; changed snapshots start a new job with its own provenance. No automatic network retries. See Schema10.
- `cancel_extraction {jobId}` -> Job. Immediate persisted cancellation; invalidates old results by generation; stops later batches. Inflight HTTP may already have been sent.
- `update_proposal {proposalId,kind,content}` -> Proposal. Pending only; preserves evidence/provenance and sets edited=true. Confirmed or rejected proposals cannot be edited.

### DTO additions

`AiSettingsPublic = {provider: "openai_compatible"|"ollama",baseUrl:string,model:string,outputFormat:"json_object"|"json_schema",timeoutSeconds:number,autoExtract:boolean,remoteConsent:boolean,configured:boolean,hasApiKey:boolean}`. configured means complete usable saved config, NOT proven connection success. All keys above required on reads.

AppState adds `aiSettings:AiSettingsPublic`. Jobs add `attempts:number,generation:number,provider:string|null,model:string|null,promptVersion:string|null,inputHash:string|null,completedBatches:number,totalBatches:number,candidateCount:number,discardedCount:number,errorCode:string|null`. kind adds extract; status adds cancelled. Source parsing status remains independent of AI state. Source-level extraction state comes from latest extract job for source (updatedAt/createdAt), with no job meaning never started.

Proposals add `origin:"manual"|"ai",provider:string|null,model:string|null,promptVersion:string|null,extractionJobId:string|null,quotes:Array<{segmentId:string,quote:string}>,edited:boolean`. Manual proposals default origin=manual, other provenance null,quotes=[],edited=false. AI evidence requires a valid segment ID in the current source/batch and an exact nonempty quote substring of it. Formal memory is created ONLY by confirm_proposal.

### Execution and recovery

Parsing completion atomically queues extraction only if saved autoExtract is enabled and configured/consented. Separate bounded worker for AI; actor never blocks on HTTP. Under Schema10, each successful batch commits its checkpoints, drafts and validated pending candidates in a short transaction; later failure preserves earlier batches and partial coverage. Invalid core evidence is rejected; organization errors use the review rules below. A valid empty array is successful zero candidates. Manual import extraction does not automatically merge or update formal memory.

Claim/progress/complete use epoch+generation and verify running status. Source hash/prompt/provider/model are snapshotted per attempt (never key). Repeated requests deduplicate. Restart recovers interrupted jobs, cancellation stays cancelled. AI config changes cancel old queued/running jobs (old endpoint work must not resume under a different setting); do not mutate completed results. Restoring a backup preserves current device settings, invalidates old worker results, and pauses restored extraction jobs until explicit user retry; no cloud requests triggered by a restored archive alone.

Schema v1 opens with transactional migration to v2 preserving manual provenance. Both v1 and v2 backups validate and restore; unknown future versions refuse. AI provenance and job fields are part of v2 backup validation.

## Phase three: local tasks, daily work and reports (authoritative)

No API key is required for task management, daily lists or report generation. Reports are deterministic LOCAL drafts from confirmed task events, with editable saved versions. AI continues to generate proposals only. Never guess personal identity from assignee strings: action=personal execution, follow_up=tracking somebody's delivery, explicitly selected by the user (source candidates default follow_up).

### Dates and events

All date-only fields use strict YYYY-MM-DD; frontend computes date using LOCAL calendar fields, never UTC toISOString slicing. Every task mutation supplies workDate (actual business date) and a clientRequestId (UUID) for idempotent retries. recordedAt is independent UTC audit time. Task changes use baseVersion. A task mutation workDate cannot precede that task's last event workDate (explicit validation error, no silent rewriting); backdated creation and chronologically recorded progress are supported. plannedDate/dueDate can be future. Historical lists/reports use immutable event snapshots as of requested date, never today's task fields. A later reopen or rename cannot change a past draft or historical completion classification.

### Task commands

- `create_task {projectId,title,description?,category,assignee?,priority,status?,progress?,dueDate?,plannedDate?,workDate,clientRequestId,memoryId?}` -> Task. memoryId must belong to project; evidence is copied from that memory's CURRENT revision only, store memoryRevision. Manual tasks have no fabricated evidence. Title required <=300 chars, description <=10000. status default todo; progress default0; done requires100. progress100 does NOT implicitly mark done. category action|follow_up, priority high|medium|low. Optional strings/dates may be null. A nonempty assignee is a free text label, never inferred as the current user.
- `update_task {taskId,baseVersion,title,description,category,assignee,priority,status,progress,dueDate,plannedDate,note,workDate,clientRequestId}` -> Task. Full form values; note required, <=10000; optimistic conflict preserves state. Appends event with before/after snapshots, actual workDate and user origin. Evidence does not silently carry into USER progress events (original task evidence remains visible separately).
- `get_task {taskId}` -> `{task:Task,events:TaskEvent[],evidence:Evidence[]}`; events newest first, including per-event original evidence when source-backed.
- `get_daily_list {date,projectId?}` -> `{date,tasks:Task[],counts:{todo,in_progress,blocked,done,cancelled}}`. Tasks as of date included if (active and (plannedDate<=date OR dueDate<=date)) OR had a task event on date. Active=todo/in_progress/blocked. Unscheduled work stays in task pool until explicitly planned. Sort active first then priority/due date. Done/cancelled from older days do not reappear merely because overdue. ProjectId absent means all projects; never cross project evidence boundaries.

Task = `{id,projectId,title,description,category:"action"|"follow_up",assignee:string|null,priority:"high"|"medium"|"low",status:"todo"|"in_progress"|"blocked"|"done"|"cancelled",progress:number,dueDate:string|null,plannedDate:string|null,version:number,origin:"manual"|"memory"|"ai",memoryId:string|null,memoryRevision:number|null,createdAt,updatedAt}`. Daily task snapshots use same shape (version represents as-of snapshot). TaskEvent = `{id,taskId,projectId,version,workDate,recordedAt,note,origin:"user"|"memory"|"ai",before:Task|null,after:Task,evidence:Evidence[]}`. A creation can be done (backfilled result), but completion date remains workDate, never import date.

### AI task proposals

AppState adds `tasks:Task[],taskProposals:TaskProposal[],reports:ReportSummary[]`. Job adds `taskCandidateCount:number` (separate from existing memory candidateCount). Existing fields remain compatible.

The model's structured output adds optional `taskCandidates:AiTaskCandidate[]`, alongside existing `candidates`. New requested schema requires both fields, runtime accepts old candidates-only responses as taskCandidates=[] for compatibility. PROMPT_VERSION increments. AiTaskCandidate = `{title,description,assignee:string|null,dueDate:string|null,dueText:string|null,status:"todo"|"in_progress"|"blocked"|"done",progress:number|null,evidence:CandidateEvidence[]}`. Only explicit absolute dates with a year are resolved; relative dates stay verbatim dueText, dueDate=null. Assignee/progress must be explicit and supported in quoted evidence. Development completion is not evidence that a wider delivery/acceptance task is done. No previously confirmed task state is sent to the model or silently modified. All-invalid task output is grounding failure; legitimate empty arrays succeed. Schema10 replaces the original whole-document transaction with atomic commits of both proposal types per successful batch.

TaskProposal = `{id,projectId,sourceId,title,description,assignee:string|null,dueDate:string|null,dueText:string|null,taskStatus,progress:number|null,status:"pending"|"confirmed"|"rejected",segmentIds:string[],quotes:Array<{segmentId,quote}>,model,provider,promptVersion,extractionJobId,edited:boolean,taskId:string|null,createdAt}`. Exact quote, scope, epoch/generation, restart, dedup and restoration controls match memory candidates. No general memories receive task statuses.

- `update_task_proposal {proposalId,title,description,assignee,dueDate,dueText,taskStatus,progress}` -> TaskProposal. Pending only; retains original evidence/model/fingerprint and edited=true. Required fields supplied, nullable values allowed.
- `confirm_task_proposal {proposalId,mode:"create"|"update",taskId?,baseVersion?,category,priority,plannedDate?,workDate,note,clientRequestId}` -> Task. create uses proposal fields, default category must be explicitly chosen by UI; update applies proposed status/progress as a REVIEWED update to existing same-project task (baseVersion required), keeps that task's existing title/assignee/priority/dueDate/category/plan, records original proposal text/quotes as this progress event. For update UI shows compared current/proposed status and progress before submission. Idempotent confirmation returns already linked task; rejected cannot confirm.
- `reject_task_proposal {proposalId}` -> TaskProposal. Confirmed proposal cannot reject.

### Daily reports

- `generate_daily_report {date,projectId?,clientRequestId}` -> DailyReport. Always local, no network. Freezes relevant task events and as-of task snapshots in report basis; creates a NEW report version for that date+scope, never overwrites an edited previous version. Repeated same clientRequestId returns same report. Sections: completion, other progress/follow-up, blocked/overdue, follow-up plans. Completion requires an event transition to done ON date and final as-of-date status still done. Reopen same day belongs in progress, not final completion; already done before date is not today's achievement. action/follow_up and assignee displayed, never calls another person's delivery "I completed". Future task changes cannot leak into old reports. No-event dates explicitly say no recorded progress. Plans are based on as-of-date facts and explicitly labeled; not promised future accomplishments.
- `get_daily_report {reportId}` -> DailyReport.
- `save_daily_report {reportId,baseVersion,content,clientRequestId}` -> DailyReport. Saves user text as NEW version (does not destroy generated or edited history); optimistic concurrency per date+scope latest version; no source event mutation. content <=100000 chars, nonempty. Edited report preserves original frozen basis and shows edited=true. No regenerated AI prose without user action.

ReportSummary = `{id,date,projectId:string|null,version:number,edited:boolean,createdAt,updatedAt}`. DailyReport adds `{content:string,basis:{events:TaskEvent[],tasks:Task[],generatedAt:string}}`. null projectId=all projects. UI supports version selection, plain Markdown editing, clipboard copy, native .md export. Never auto-send a report to a colleague/platform. Core reports include task IDs and source references in basis so UI can open task/evidence.

Desktop `export_report {reportId}` -> `{cancelled:boolean,path?:string}` opens native save dialog and writes report content obtained from Rust, never an arbitrary renderer filesystem path. QA bridge adds GET /reports/:id/download for isolated dev only.

### Persistence

Schema3 transactional migration preserves v1/v2 sources/memories/AI provenance. Tasks/events/proposals/report versions/idempotency records join consistent backups and full type/domain/evidence validation. v1 and v2 archives restore and migrate; unknown future schema refuses. Existing restored import/extract pause rules remain unchanged. Default daily page uses client date 2026-10-19 when applicable; do not hardcode it in product code.

Phase3 desktop also adds `copy_report {reportId}` -> `{copied:true}`, writing the Rust-stored report through native clipboard; renderer does not receive general clipboard-read access. Counts for v3 backups add `tasks,reports` (report version count); old backup counts may omit these and UI displays0. Restore inspection must show task/report differences too. Existing counts fields remain unchanged.


## Schema 4: source ingestion and memory maintenance

- `get_feishu_sources {}` → `{settings:{enabled,intervalSeconds,sources:[{kind:"chat"|"document",target,projectId,enabled,historyDays}]},syncing,statuses,lastError}`. Source start anchors are server managed. Only explicitly selected sources are read; document URLs are validated as Feishu docx/wiki references. No arbitrary URL fetching.
- `save_feishu_sources {enabled,intervalSeconds,sources}` → same status. Validates existing project IDs, source identity uniqueness, intervals60–3600 and lookback1–30 days. Source settings and cursors are device-local, excluded from archives.
- `sync_feishu_sources {}` → `{queued:true}`. Queues asynchronous read/import work; inspect source statuses for completion. No reply is sent by ingestion.
- `get_memory_maintenance {}` → `{settings:{enabled,idleSeconds,dailyCalls,autoNew,revision},callsToday,blockedReason,reviews,runs,origins}`. Defaults: enabled=true, idleSeconds=120, dailyCalls=100, autoNew=true. `get_state` adds `memoryReviewCount`.
- `save_memory_maintenance {enabled,idleSeconds,dailyCalls,autoNew}` → settings. Validates idle30–3600 and dailyCalls1–2000; cancels stale work through a new configuration revision.
- `memory_activity {}` → `{ok:true}`. Debounced actual user input only; polling must never call it.
- `run_memory_maintenance {}` → `{queued:true}`. Explicitly runs one item even when scheduled maintenance is disabled; respects saved model permissions and daily budget.
- `retry_memory_maintenance {}` requeues failed comparisons. Extraction retries use `retry_extraction`.
- `recompare_memory_review {reviewId}` discards a still-pending comparison and queues fresh comparison; never changes formal memory.
- `resolve_memory_review {reviewId,action:"new"|"replace"|"mergeEvidence"|"ignore",baseRevision?,content?}` → `{resolved:true}`. Public calls cannot set automatic provenance. Target mutations require both reviewed and current revisions to match. New/replace may use user-edited content; mergeEvidence preserves current content and prior evidence.

Comparisons use current same-project memory with bounded model input, occurrence/revision metadata, exact-quote proposals and immutable source snapshots. Incomplete context cannot auto-admit new facts. Only Feishu-collected sources auto-apply independent new facts (if enabled) or literal duplicates; manually imported candidates remain pending. Conflicts and semantic duplicates need user review. Each accepted change creates a revision with evidence; `automatic` is visibly distinguished from human confirmation.

Workspace epoch, configuration revision, model revision, source/job generations, proposal and memory snapshots plus user-activity generation guard commits. Worker HTTP runs outside the actor. Counters reserve each network model call before dispatch, including failed/ambiguous requests; deterministic local comparisons do not consume calls. Restoration pauses scheduled work and keeps the larger local daily usage counter, so old archives cannot refund requests. Secrets, subscriptions, cursors and reply receipts never enter project archives; source provenance, memory reviews and run histories do.

Unresolved pending conflict/uncertain reviews with a target temporarily exclude that target from QA retrieval; the same check before sending invalidates an answer started before the conflict appeared. Resolution restores eligibility without deleting historical memory.


## Schema 5: reviewed workload and daily capacity planning

- `get_daily_planning {date,projectId?}` returns dated `capacity` (nullable), scoped active `tasks`, `estimates`, `relations`, that date's `allocations`, latest scoped `drafts` with stale flags, latest applicable `confirmedPlan`, bounded context counts and `modelAvailable`. Polling does not count as user activity.
- `save_daily_capacity {date,minutes,bufferMinutes,baseRevision}` explicitly sets that date's personal capacity. Integer minutes0–960, buffer0–minutes, optimistic revision (null on creation). Past dates are immutable. No default/carry-forward capacity.
- `save_task_estimate {taskId,baseVersion,baseUpdatedAt,minutes}` explicitly confirms5–1440 integer minutes. Task version and prior estimate timestamp (null on first estimate) must match.
- `analyze_task_workload {date,projectId?,useModel?:boolean}` captures actor snapshot, performs bounded grounded structured analysis outside actor, saves pending analysis only if snapshot still current. Default useModel=true, saved material consent required. useModel=false suggests literal duplicates and existing pending source task proposals. No task mutation.
- `preview_task_relation {date,projectId?,kind:"dependency"|"blocker",taskId,targetId:string|null,reason}` creates a one-change pending review; dependency means taskId waits for targetId. Same project, no self-reference.
- `generate_daily_plan {date,projectId?,durationOverrides?:Record<taskId,integer>,skipTaskIds?:string[]}` creates pending deterministic dependency/capacity preview. Requires saved capacity. Unknown task overrides rejected. Result contains `items`, `deferred`, `commitments`, totals, date changes, reasons, assumptions and conditional prerequisites; no task mutation.
- `confirm_planning_draft {draftId,selectedIds:string[]}`: analysis requires nonempty explicit chosen suggestion IDs; schedule requires[] and confirms complete reviewed plan (partial changes require regenerated preview). Snapshot guards include task versions, source/memory/proposal snapshots, estimates, graph, allocations, daily capacity, model revision and workspace epoch. Atomic transaction; cyclic graphs and merge chains rejected, no cross-project edges. Same applied selection is idempotent.
- `dismiss_planning_draft {draftId}` dismisses pending suggestion with no task changes.
- `remove_task_relation {relationId,createdAt}` confirms deactivation of one dependency/blocker. History retained. Does not change task status.

Capacity is shared across projects; scoped plans reserve other-project same-day commitments plus same-day done work. Action predecessors may be sequenced in one day with explicit conditional wording. Follow-up effort never proves delivery and cannot unlock a dependent task. Scheduling does not change task status/progress/owner/deadline. Future planned dates are kept; non-fitting same-day items explicitly preview clearing plannedDate to null; no automatic next-day promises. Confirmed duration/order/reasons are separately persisted; task date changes enter normal user task events. Merge cancels source tasks with notes, keeps target fields, redirects dependencies/blockers and preserves history. Reviewed source task proposals can apply status/progress as shown; memory-based new tasks are unscheduled follow-ups with unassigned owner/deadline.

Model evidence must be a same-project literal quote from the supplied catalog; memory_task and proposal changes must cite their respective source object. Current memories with pending conflict/uncertain reviews are excluded. Latest ready remote object version is used for Feishu original excerpts. Full scoped active task inventory is retained; descriptions and material excerpts are bounded, coverage limitations displayed. Up to100 suggested changes. No credentials, privileged commands or source instructions enter control flow.

Schema5 adds planning_capacity,task_estimates,task_relations,planning_drafts,daily_allocations. Snapshot fingerprints, authentic historical task snapshots, analysis grounding, graph validity, deterministic schedule equality and allocation/draft consistency are validated during backup inspection. Restoration preserves confirmed planning history and invalidates pending drafts. Device Feishu credentials/settings remain excluded.

## Schema 9: organized assertions and bounded answer claims

- `revise_memory` accepts optional `facets: {entity?,topic?,role?:""|"owner"|"approver"|"contact",conditions?:string[],validFrom?:string|null,validUntil?:string|null}`. Text values must occur in current content, at most160 characters each, at most8 conditions. Validity dates are explicit YYYY-MM-DD dates in content, with from<=until. Approval duties alone cannot be labelled owner. An omitted facets object clears annotations on the new revision; historical annotations remain immutable. `get_memory.revisions[].facets` returns the stored organization or `{}`.
- AI memory candidates optionally parse old responses without facets for compatibility; the new extraction schema requests them. New candidate facets are validated against content and actual quotes, displayed with the proposal, and promoted only on confirmation. Editing proposal content clears stale annotations atomically.
- Project QA accepts optional `asOfDate` for explicit validity checks (default local date). Desktop uses its existing `date`. These dates filter confirmed validity intervals; they do not reconstruct superseded revision history.
- Generation requires `grounded,status,claims,unknowns`. Each grounded claim contains nonempty `text` (<=600 characters) and `supportSpans:[{referenceIndex,spanIndex}]`, with1–12 unique span selections and at most6 references; at most12 claims. Both indexes start at1 and must address the exact caller-supplied reference list. Models do not copy UUIDs, quote bodies or citation unions into their output. Rust resolves selections to the trusted original IDs and exact current-content `supportQuotes`, rejects missing/out-of-range/duplicate or ambiguous bindings, and applies the existing length, citation-union and anchor validation. Free-form prose is not a successful answer protocol.
- `indexed_references` partitions each supplied current `content` into contiguous spans of at most600 Unicode characters, preferring sentence/newline boundaries after300 characters. Joining all spans exactly reproduces that supplied body, including whitespace; this is neither summarization nor relevance-based sentence omission. Empty facets, duplicate title/sourceTitle, and generation-stage revision/update metadata are removed from the projected input. A nonempty memoryId is omitted only when id exactly equals `memory:` plus that memoryId. Only a list whose every reference has the exact same nonblank projectId carries projectId on its first item and inherits it for later items. Only within that common project, a sourceTitle exactly shared by every item and nonblank is likewise carried once on the first item. Mixed/empty/missing projects disable both inheritance rules; differing/empty/missing source titles disable source-title inheritance. Originally missing projectId/sourceTitle become explicit null in model projections to prevent mistaken inheritance. Other supplied ID/value combinations remain intact. Stable IDs remain trusted binding/audit metadata. Runtime original references, bodies, facets/conditions, scope and revision checks are unchanged; public results retain original IDs, revisions, evidence and expanded anchors.
- Answer results add `status:"answered"|"partial"|"unknown"|"conflicted"`, `claims`, `unknowns`, `unknownsPresentation`, and `claimValidation`. Up to6 raw unknown items, each<=2000 characters, remain available to review and targeted search; display strings and rendered prose clip each item to300 characters including an ellipsis. Display clipping must not alter support, completeness or refusal decisions. `claimValidation.version` is `indexed-current-spans-v2` for expanded compact output; internal legacy anchored callers retain `atomic-anchors-v1`. `grounded=true` covers answered and partial; binding validation is not semantic accuracy. Local answers may omit claims, structured field reads retain `queryMode=structured_field`.
- Focused desktop model contexts are bounded to24 total references and36000 projected characters; memory references may occupy24 slots, other kinds at most6 each. Overview contexts retain40 total references and40000 projected characters, with memory<=24 and other kinds<=20 each. Connector contexts contain at most24 memories and36000 projected characters. Capacity measures the model-facing reference projection; raw evidence and backing records remain available for validation/UI but do not consume this model-reference budget. Desktop retrieval version is `personal-assistant-v9-target-obligations`, connector is `confirmed-current-memory-v8-target-obligations`, context pack is `current-content-pack-v2-indexed-spans`.
- Retrieval trace version is `organized-memory-v8-data-provenance`, index backend `fts5-derived-v3`, derived term marker `lexicalschema3`. English stopwords and conservative morphology supplement exact matching; exact spelling retains higher weight. Exact irregular plural `corpora` maps to `corpus` without matching longer names containing that string. BM25 statistics use the full eligible scoped body corpus, bounded to10000 records/32MiB. FTS is a derived navigation cache and does not define fact eligibility. Old cache markers, including `lexicalschema2`, missing entries and changed revisions rebuild lazily; restore discards derived cache contents. The provenance classification change does not change indexed terms or require a new cache schema.
- Only concrete names form entity bindings; English name matches require complete word boundaries. Generic subjects such as `we`, `the model` and `our approach` do not bind a named scope or exclude other entities. Original facets are preserved; concrete entity mismatches and explicit validity intervals still restrict eligibility, and generic/untagged records cannot be assigned an inferred subject. Context deduplication requires equal project, kind, exact body and facets; differing conditions, roles, dates or contradictory text stay distinct.
- Ranked direct matches interleave at most one confirmed neighbor after three direct matches, at most6 neighbors in24 slots. The leading matches supply up to6 independent ready-source/ordinal anchor groups; multiple hits in one segment do not consume separate anchors. Each candidate belongs to its closest anchor, same-segment evidence precedes adjacent ordinals, and groups are traversed in rounds. Within a segment, exact positions of the current anchor/candidate bodies prioritize nearby preceding/following sentences. Missing exact positions use lexical score and stable body/facet order, not random UUIDs, as fallback. Source positions only reorder already-confirmed current candidates; they cannot add unconfirmed paragraph facts or override project, correction, revision, conflict, facet or validity guards. Trace ranking records `selectionReason=direct_lexical|adjacent_confirmed`, `exactDuplicatesCollapsed` and `adjacentConfirmed`.
- Broad data/corpus questions without a concrete entity binding or explicit component target can interleave at most`min(limit/6,4)` same-ready-source data-origin/study-declaration candidates while retaining a majority of direct matches. Candidates identify explicit acquisition or use/training with a named/public data resource, excluding computed score/feature transformations. Origin checks inspect the object before the first from/via/source marker; obtained improvements, sampled role labels/parameters and generated latent variables cannot qualify merely because later text mentions data. Existing counted acquisition, public-origin, literal data-extraction and Chinese acquisition paths remain; first-person run/conduct/perform experiments on/using a named data resource also qualifies. Distinct source segments are offered before repeating one stage, with the same4-slot and total-reference limits. These rules change navigation selection within the existing eligible pool, not candidate recall or fact eligibility. Explicit encoders, classifiers, submodels and other component targets skip this path. `selectionReason=data_provenance|study_context` and `sourceNavigation` are navigation cues only, not inferred main-task identity or answers. Generation/review must distinguish study, component, prior work, stages and statistical denominators.
- Every model-generated grounded answer receives `claim-support-v8-explicit-claim-indices` review with `supported,answersQuestion,completeAnswer,obligations,unknownDecisions,unsupportedClaims,missingAspects,reason`. Review receives selected support spans and complete cited current numbered bodies, restoring update timestamps; other body spans may expose limitations but cannot replace an incorrect support span. The rendered answer and duplicate quote bodies are not retransmitted. Structured field reads/local-only answers do not incur this model review.
- `obligations[]` contains1–6 `{target,status,claimIndices}` items. Target is a nonempty phrase<=100 characters; status is `answered|partial|missing`. Answered/partial obligations require unique valid1-based indices into existing claims; missing obligations require no claim indices. `answersQuestion` must equal whether any obligation is answered/partial, and missing/partial obligations require explicit missingAspects. Obligation granularity comes only from the question; unknowns and references cannot expand it. Overall/yes-no questions do not automatically require per-group enumeration or quantitative aggregates, metrics do not imply every submetric, mechanisms do not imply dimensions/batching/complexity, and a requested group's count does not imply a whole-study count. Explicit targets, baselines, relations and methods remain necessary. Background or another object cannot semantically fulfill a requested obligation.
- `unknownDecisions[]` must cover each original unknown exactly once with unique1-based `unknownIndex`, `disposition:"retain"|"unasked"|"answered"`, and `claimIndices`. Retain/unasked decisions require empty claim indices; answered decisions require existing claims used by an answered obligation. A summary completeAnswer flag cannot delete uncertainty by itself. CompleteAnswer must match supported=true, all obligations answered, no retained unknown and empty missingAspects. Applying valid decisions can only refine uncertainty and rerender existing claims; all original binding checks run again. Necessary missing targets, comparison baselines, shared-parameter relations or computation methods cannot be dismissed as unasked details merely to make an answer complete.
- Review input labels every checked claim with an explicit1-based `claimIndex`. Output claimIndices arrays can only select those supplied IDs: their schema enumerates the actual1..N claim range. They cannot copy referenceIndex or invent numbering. Runtime range/duplicate checks still reject invalid indices without permissive remapping.
- A structurally valid supported/direct review with completeAnswer=false may mark all coarse obligations answered while explicitly retaining an unknown or missingAspects. Only that narrow case normalizes conservatively to partial; it cannot infer completeness or clear retained uncertainty. Audit preserves the original `rawReview` and adds `effectiveStatus=partial` and `normalization=coarse-answered-with-explicit-gaps`. Index, per-unknown coverage and support checks remain mandatory; completeAnswer=true with retained/missing gaps still fails validation.
- Retained original unknowns are preserved within the existing6-item answer limit. Additional necessary review gaps that do not fit are retained under `qualityReview.unrenderedMissingAspects`, keep the result partial and remain available to targeted search; they do not silently replace retained uncertainty or overflow the answer contract. Raw unknown<=2000-character and display<=300-character limits remain unchanged.
- For generic task/model/data and component/comparison ambiguity, review may receive at most2 uncited current `scopeCandidates`, each with<=220 content characters and<=1800 serialized JSON characters in total. They are constrained to current visible project/source-title scope and explicitly marked `notSupport:true`. These snippets can help detect answering a component instead of the requested task, but cannot support new claims, repair wrong anchors or substitute for cited references. No additional model call is introduced.
- Rust guarantees index/range/count, per-item coverage, summary consistency and current-snapshot checks. Whether the obligations correctly capture the user's question, an unknown is genuinely unasked, a component matches the target, or a claim is semantically supported remains a fallible model judgment; protocol validity does not establish semantic reliability.
- At most one supplement is attempted. Review transport/format unavailability stops rather than initiating a new search. A first grounded partial already passing binding and semantic supported/direct-answer review can be retained if the supplement fails; returning it revalidates both its original snapshot and the current snapshot. No unreviewed new claim receives fallback trust. Unchanged question/project/date/preferences/scope/version envelope fields and exact equality of complete `model_reference` projections keyed by nonempty stable identity permit skipping second generation/review even when identical facts only reorder. Missing or duplicate identities, or changed projected bodies/facets/conditions, do not qualify. Both complete snapshots are still validated, the original answer retains its original reference mapping, and `supplementStatus=UNCHANGED_CONTEXT` is recorded. Rewrite strings are excluded from generation input.
- `queryTrace` adds `retrievalMs`, per-request `stages` (name,elapsedMs,inputChars,usage or null,errorCode),`reportedTokens`,`usageComplete`,`reportedTokenStopThreshold=60000`,`tokenBudgetMode=provider-reported-post-call`, review history, and zero-based `answerGenerationIndex` identifying the actual returned generation. `reviewedPartialFallback=true` points to generation0 without inventing another call; supplement errors and real generation ordering remain visible. Flow version is `bounded-question-flow-v6-explicit-claim-indices`, with `unknownReviewMode=individual-obligation-decisions`, `reviewScopeMaxCandidates=2`, `reviewScopeMaxChars=1800`. Caps stay at one supplement round,5 model calls,180000 cumulative input/schema characters,16000 parsed output characters per call and the original shared timeout. A full sequence can be generation, review, rewrite, generation, final review. Strict `json_schema` sends one provider schema; `json_object` retains one user-input schema. No exact tokenizer is installed;60000 reported tokens is a post-response stop threshold and missing usage is never reported as zero. There are no automatic network retries.
- Schema9 adds revision/proposal facets and a rebuildable FTS5 cache plus ordinary primary-key revision mapping. Cache contents are excluded from compressed backup snapshots and discarded on restore. Backup validation checks canonical facets and expected cache columns; no database triggers are installed.

## Schema 10: recoverable extraction and graded organization review

This section supersedes historical extraction commit/retry descriptions above. The initial v5 extraction-only implementation kept QA fixed; its archived20-question development run did not pass the gate. The completed v6 extraction round jointly changed literal extraction, model-facing reference projection and status normalization while retaining its then-current retrieval quantities/order. Those historical gains cannot be attributed solely to extraction. Subsequent retrieval/QA-efficient rounds and the current QA-calibration round retain that v6 extraction behavior and exact citation/anchor checks, while changing retrieval and model protocols under the current contracts above.

### Model capacity and task guards

- Extraction prompt version: `project-memory-task-extraction-v6-literal`. Prefer one or two verbatim complete source sentences per fact; preserve subjects, pronouns, names, numbers, math/LaTeX, capitalization, negation and conditions, then derive optional organization from identical spans in content and source quotes. Do not rewrite a subject or notation in content while leaving a mismatching scope label. A missing optional field may be generated empty initially; already generated invalid scope is still quarantined. Initial material batches contain at most2400 Unicode characters, using paragraph/sentence boundaries and at most256 characters of overlap for long fragments. Capacity failures may split a batch to depth2; parent requests remain recorded and charged to the task.
- Each response requests at most6144 output tokens. Schema and runtime limits agree: at most12 memory candidates,4 task candidates,16 total; memory content/task description <=600 characters, title/assignee <=300 characters, at most3 evidence quotes per candidate, each quote <=800 characters, response body <=2MiB. Exceeding a limit produces a capacity error. Exactly reaching the candidate limit can still succeed and is not proof of complete fact coverage.
- Guards:512 requests,3,000,000 provider-reported plus conservatively reserved tokens,20 minutes active task time. There is no exact tokenizer: reservation uses the complete serialized request and output allowance. Unreported usage is retained as a reservation, never treated as zero; in-flight time is reserved before sending and reconciled on a terminal checkpoint. Thresholds are operational guards, not a guaranteed invoice cap.
- Only attributable capacity errors receive bounded splitting. Authentication, service, rate-limit, network, filtering, JSON and schema failures do not automatically replay. Explicit retry is required for a failed job. Ordinary process restart can recover interrupted queued/running work; cancelled work stays cancelled.

### Durable state and DTOs

Schema10 adds `extraction_batches`, `extraction_drafts` and `extraction_budget`. They join transactional migration and backup inspection/restore.

- A checkpoint binds the job, source/input hashes, saved model configuration revision, prompt version and deterministic batch plan/key. Checkpoint events append `started|succeeded|split|failed`, parent key, raw model output when available, usage, error and cumulative budget. The database actor persists a `started` reservation before a network request; model HTTP remains outside the actor.
- A successful batch atomically stores raw candidates, organization issues, releasable pending proposals and task proposals. A subsequent failure leaves those rows intact; job status and `completedBatches/totalBatches` continue to describe incomplete processing. Completion counts existing job proposals and does not reset them because the final batch added zero rows.
- `get_state.extractionDrafts[]` = `{id,jobId,sourceId,projectId,batchKey,candidate,facets,issues,status,proposalId,reviewReason,createdAt,reviewedAt}`. `candidate` preserves the original `{kind,content,evidence,facets}`; `facets` is the isolated/accepted organization or reviewed value. `issues[]` = `{field,reason,severity,value?}` with severity `navigation|applicability|fact`. Status is `ready|needs_review|rejected|reviewed`; proposalId is null until a releasable proposal exists.
- `get_state.extractionBatches[]` is the latest compact state for each persisted batch key: `{jobId,sourceId,batchKey,parentKey,status,inputHash,discardedCount,usage,errorCode,budget,completedBatches,totalBatches,checkpointCount}`. `budget` = `{requests,inputTokens,outputTokens,unreportedTokens,usageComplete,elapsedMs,pendingElapsedMs}`. It is cumulative: use the highest cumulative record, not a sum across batches. `checkpointCount` counts stored events, not model requests. Raw response bodies stay in SQLite and do not enter this DTO.
- Neither drafts nor pending proposals are formal retrieval input. Manual imports require `confirm_proposal` after review; existing opt-in remote-source maintenance confirmation policies still govern releasable Feishu candidates.

### Graded validation and commands

1. Empty/invalid body, source or literal quote cannot produce a confirmable proposal. Raw batch output and rejection evidence remain available for audit.
2. Invalid `topic` is quarantined independently. Preserve its raw value and reason while accepted facets omit that navigation label; valid facts and applicability fields can continue to pending confirmation.
3. Invalid/conflicting `entity`, `role`, `conditions`, `validFrom` or `validUntil` produces a `needs_review` draft without a proposal. Never turn a failed applicability field into an empty/unknown field and directly confirm it. Conditions cannot contain empty, whitespace-only or duplicate placeholders.
4. Valid facets require literal support in the current body and actual source quotes. This remains a structural grounding check, not independent semantic verification of every assertion.

`review_extraction_draft {draftId,action:"approve"|"reject",reason,content?,facets?}` → `{draftId,action}`.

- Only `needs_review` drafts can be reviewed. Reason is required and <=1000 characters. `reject` records the reason while preserving original output. `approve` requires nonempty content and an explicit facets object, revalidates current source scope and quotes, saves a reviewed draft and creates/deduplicates a pending proposal; it does not create formal memory.
- Approval cannot clear any originally nonempty entity/role/validity field or reduce the number of original conditions. Empty/duplicate condition placeholders do not bypass validation. The current UI offers body/entity/topic/role/condition/date fields, evidence navigation, reason and an explicit human review checkbox. A draft that cannot be corrected can be rejected.
- `confirm_proposal` also guards the draft's releasable review state and current source version. Deduplication includes normalized body and accepted facets; equal text with different applicability fields does not overwrite the earlier candidate.

### Recovery, budget accounting and verification

Same-snapshot retry loads successful leaf batches and split parents without calling them again; failed/in-flight batches retain their spent or uncertain budget. New configuration/prompt/source snapshots start a new extraction job rather than relabelling archived output. Epoch/generation, running state, source version and restore-journal guards reject stale worker writes. Manual and idle extraction use this same checkpoint protocol. Idle daily budget is reserved only for actual `started` network attempts, not cached batches or local comparisons.

Backups retain invalid raw facets in reviewable drafts, while validating accepted proposals, source/project associations and formal revision organization. Restore pauses extraction and preserves the current device model settings. `extraction_budget` retains the pre-restore high-water state for the same job/snapshot so an older archive cannot refund requests/tokens/time already spent. A budget-only resume checkpoint can preserve cost without claiming that facts lost during restore are cached successful output. Ordinary backup restoration cannot launch model requests by itself.

### Current model-reference and answer-status normalization

`answer_contract::model_reference` first projects supplied references to `id,memoryId,content,title,sourceTitle,kind,projectId,revision,updatedAt` plus the six accepted facet fields. `indexed_references` then deterministically partitions the supplied current body into complete numbered spans, omits empty facets and duplicate title, and removes revision/update fields from generation metadata. It omits memoryId only for the exact nonempty alias `id=memory:<memoryId>`. A common exact nonblank projectId shared by every list item appears explicitly only on the first; an exact nonblank common sourceTitle can inherit only within that same common project. Mixed/missing/empty projects or inconsistent source titles do not gain inherited metadata. Originally missing project/source fields become explicit null in model input. These projection savings do not alter authoritative runtime references, bodies, conditions or scope/revision validation. Review restores update timestamps and retains the complete cited current bodies plus selected supports; the model never supplies the authoritative original-ID mapping. No raw `evidence`, full `record` or other nested backing data enters these model prompts. Trusted UI/API results retain original revisions, full evidence, backing records and expanded exact anchors for navigation/audit. Context capacity measures the model projection, and shared memory selection order is preserved rather than reranked by a common source title.

After every claim text, exact anchor, citation union, length and field check succeeds, `status=answered` with nonempty valid `unknowns` first normalizes to `partial`, retaining full raw unknowns for review. Every original item requires its own validated unknownDecisions disposition; completeAnswer alone cannot clear it. Rendering answered additionally requires supported, all requested obligations answered, no retained unknown and no missingAspects, without changing facts/anchors and after rerunning binding checks. Raw unknown items stay bounded to2000 characters and presentation to300. Necessary gaps beyond the6-item answer limit remain in qualityReview.unrenderedMissingAspects and targeted-search input. Invalid anchors/citations/unknowns still fail; no invented fact or protocol error becomes a grounded response. Existing `partial` requires uncertainty. Expanded compact output uses `indexed-current-spans-v2`; internal legacy anchored calls retain `atomic-anchors-v1`.
